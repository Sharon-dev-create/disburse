## 5. Role verification and lifecycle

Source and generated ABI, not role names, determine permission requirements:

| Action | Actual permission / prerequisite |
| --- | --- |
| Add/remove accepted token | Owner only |
| Grant/revoke non-owner role | Owner only; cannot self-grant or grant Owner |
| Create campaign | Any caller; contract unpaused; valid title and positive budget |
| Approve campaign | Administrator (owner implicit); Draft → Approved |
| Accept campaign FT funding | Allowlisted predecessor token; matching token; Approved campaign; bounded positive amount |
| Activate campaign | Explicit Operator; Approved → Active |
| Create payout/reservation | Operator or Administrator; Active; input token matches; positive amounts; available funded balance |
| Record settlement / verifier recovery | Explicit Verifier plus evidence/status validation; outside this milestone |

Minimum next-milestone roles: owner uses implicit Administrator; grant only
Operator to `disburse-op-b966e36d.testnet`. Use the same account for funding to
minimize identities. Verifier: **not required or proposed** for reservations,
budget enforcement and read-only accounting. No extra Administrator needed.

Actual assignments on both live deployments: owner is `disburse-topg.testnet`
with implicit Owner and Administrator; no explicit role records. Explicit
Operator checks for the proposed operator are false on both. Full state inventory
also establishes absence of other direct roles, rather than assuming the queried
account list is exhaustive. USDC allowlist check=false on both; state inventory
shows no other token entries.

Future sequence: **Draft → Approved → fund while Approved → Active → Reserved
payout**. Active ↔ Paused campaign transitions use Operator/Admin; cancellation
from Draft/Approved allows creator/Admin and from Active/Paused requires Admin.
No public campaign-completion method was found. Payout execution can progress
Reserved → Executing → PendingVerification → Succeeded only through additional
operator/verifier methods and validated evidence; none is planned here. Recovery
methods and their tests are out of the configuration transaction scope.

Relevant ABI shapes (descriptive placeholders, not transaction commands):

- `create_campaign`: `{title: string, token_id: AccountId, budget: u128 number}`.
- `approve_campaign` / `activate_campaign`: `{campaign_id: u64 number}`.
- `create_payout`: `{campaign_id: u64, idempotency_key: string,
  recipient_near_account_id: AccountId|null,
  destination: {chain_id: string, recipient_address: string},
  input_amount: TokenAmount, expected_output_amount: TokenAmount}`.
- `TokenAmount`: `{token_id: {Near: AccountId}|{External: string},
  atomic_amount: u128 number, decimals: u8 number}`. These raw u128 fields are
  JSON numbers, unlike U128 view fields and NEP-141 transfer amounts (strings).
  Preserve large integers without JavaScript Number rounding.
- Future FT call uses `receiver_id` equal to selected contract, `amount` as an
  atomic decimal string, `memo` optional/null and `msg` a JSON string encoding
  `{"campaign_id":<numeric u64>}`. Do not call `ft_on_transfer` directly.
