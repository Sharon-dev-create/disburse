# Milestone 5-A — Security threat model

**Design only, 2026-11-15; no mitigations are claimed implemented.**

Scope and baseline: [architecture](milestone-5-native-payout-architecture.md).
Critical controls protect custody and exactly-once spending; high risks block deployment
until implemented and tested. Residual root/token/recovery trust requires explicit acceptance.

| ID / severity | Threat and preconditions | Impact | Proposed mitigation | Residual risk | Required test |
| --- | --- | --- | --- | --- | --- |
| T01 Critical | **Unauthorized execution / compromised Operator**: Operator creates a payout and tries to execute without independent consent. Preconditions: Operator role or API access. | Unauthorized custody loss. | Explicit on-chain NativeApprover approval, separate actors, fixed reservation and NativeExecutor role; reject legacy bypass. | Owner can change permissions; colluding principals remain trusted. | No-role, Operator-only, self-approval and all legacy mutation bypass tests. |
| T02 Critical | **Duplicate spend after callback loss**: Token delivered but callback panics; worker assumes failure and retries. Preconditions: Successful token receipt with missing callback state. | Same payout paid twice. | Consume approval and lock attempt before promises; keep reserved; no timeout retry; dual evidence-based bookkeeping recovery. | Colluding recovery attestors can falsely assert failure. | Real transfer success plus callback panic/OOG, restart and attempted duplicate. |
| T03 Critical | **Legacy manual settlement or release bypass**: Verifier settles nonexistent native delivery or releases an unresolved transfer. Preconditions: Native payout accessible through legacy methods. | False spent or newly spendable delivered funds. | Immutable native mode; reject every legacy settlement/failure/release/execution-confirmation route for native records. | Coverage omissions are catastrophic. | Method-by-method negative matrix including paused and ManualReview paths. |
| T04 Critical | **Unsafe migration / rollback**: Changed Borsh fields or old WASM ignores sidecar locks. Preconditions: Deployment authority or incompatible build. | Lost state, lost replay protections, duplicate transfers. | Preserve old bytes, version sidecars, full snapshot fixtures, freeze and forward fix; no automatic rollback. | Root deployer can install arbitrary code. | Old snapshot including nonempty indexes; candidate/old-code behavioral compatibility tests. |
| T05 Critical | **Root FullAccess compromise**: Account key signs direct token transfer or installs malicious WASM. Preconditions: Contract account FullAccess access. | Complete loss bypassing app caps/roles. | Exclude root keys from service, secure separately approved deployment process, monitor keys/code and freeze operations on drift. | Cannot prevent root bypass while FullAccess remains; no permission change authorized now. | Demonstrate trust boundary locally and reject service root-key configuration. |
| T06 High | **Compromised execution service / API token**: Backend submits altered payout or fabricates job success. Preconditions: Service compromise. | Wrong recipient/payment or false UI settlement. | On-chain approval binding and roles, scoped future signer, chain-first reconciliation, readonly deployment kept separate. | Compromised permitted executor can cause delay/gas spending within approvals. | Alter each binding field, mock backend success without token receipt. |
| T07 High | **Duplicate execution concurrency**: Two workers or retries race on same payout. Preconditions: Lease expiry, restarted process or duplicate events. | Two transfer promises. | Single on-chain active attempt and approval consumption; immutable mode/idempotency; DB fencing supplementary. | Gas wasted on rejected calls. | Concurrent execute calls, stale DB leases and auth consumption races. |
| T08 High | **Callback spoofing / stale callback**: Attacker calls callback, or old attempt result targets new attempt. Preconditions: Public callback or missing identity check. | False settlement/retry state. | Private predecessor=current; one result; payout/auth/attempt check and applied marker; preserve state on mismatch. | Root self-call remains privileged; depends on deployment integrity. | External/contract caller, wrong result count, wrong auth, stale and duplicate callbacks. |
| T09 High | **Cross-contract interleaving**: Pause, another payout callback or campaign change occurs between receipts. Preconditions: Asynchronous promises. | Stale accounting overwrite or unauthorized dispatch. | Persist lock first; reload current accounting; recheck before dispatch; allow safe completion while paused. | Late callback may require review after governance changes. | Interleave two payouts and campaigns, pause/revoke/expire between stages. |
| T10 High | **Amount / token / decimals manipulation**: Alter expected output or token after approval. Preconditions: Loose legacy destination/amount validation. | Overpayment, wrong asset or misleading UI. | Strict native identity, same input/output atomic amount, decimals6, stored digest, no arbitrary execution args. | Trusted token implementation can violate semantics. | Token, amount, decimals, mode and output mismatch tests. |
| T11 High | **Recipient substitution / false control**: Approved destination swapped or NEP413 replay used. Preconditions: Mutable recipient or weak proof validation. | Irrecoverable transfer to attacker. | Immutable recipient, explicit allowlist, independent control proof/nonce/domain/expiry/current key membership and storage check. | Key theft after proof; allowlist governance compromise. | Mutation, replay, wrong account/key/domain/network and expired proof tests. |
| T12 High | **Budget / cross-campaign bypass**: Pooled balance used to fund unfunded campaign or double reserve. Preconditions: Arithmetic or campaign binding bug. | Another campaign loses funds. | Checked invariant arithmetic, exact reservation amount and campaign binding; surplus not autoallocated. | Out-of-band root or token movements can break custody. | Boundary u128, exhausted budget, multiple payouts/campaigns and unsolicited token surplus. |
| T13 High | **Incorrect evidence / colluding recovery**: Hash/log/balance accepted as proof, or false nonsettlement attested. Preconditions: Recovery authority or unverified RPC. | Double payment or false terminal state. | Canonical finalized receipt graph from two RPCs, exact binding, two distinct attestors, no unresolved retry/release. | Attestation is trusted, not on-chain cryptographic receipt verification. | Forged hash/log, missing receipt, conflicting RPCs, same-person dual approval. |
| T14 High | **Token failure or malicious upgrade**: Token rejects storage/transfer, freezes accounts or returns success without transfer. Preconditions: Trusted token behavior changes. | Frozen funds or falsely recorded delivery. | Pinned account and monitored code identity, source/conformance gate; reject upgrades/drift; bounded failure handling. | No atomic remote code-hash pin; token governance remains trusted. | Mock reject/no-op/nonstandard return and upgrade-between-preflight tests. |
| T15 High | **Callback gas/storage exhaustion**: Token commits but callback lacks gas or storage balance. Preconditions: Underbudgeted graph, large evidence strings. | Delivered but unsettled locked payout. | Bounded preallocated records, measured gas margins, minimum prepaid guards; preserve attempt and review on callback loss. | No retroactive gas top-up; liveness can stop. | Real sandbox OOG/storage pressure plus no-resend assertions. |
| T16 High | **RPC inconsistency / timeout**: Timeout interpreted as failed submission. Preconditions: Unreliable endpoint or stale finality. | Duplicate send or wrong evidence. | Pinned finalized block, two endpoints, canonical receipt traversal; timeout→unknown. | Two endpoints may share infrastructure; no light-client proof. | Timeout before/after submission, divergent endpoints and missing history. |
| T17 High | **Database crash / restart / stale lease**: Crash after chain dispatch but before DB commit. Preconditions: Nonatomic DB/chain workflow. | Duplicate send or lost observation. | Chain attempt authority, durable outbox/attempt intent with fences, replayable discovery, resume observation not transfer. | Manual intervention may be required; DB durability not chain authority. | Real PostgreSQL crash-boundary and lease-expiry concurrent-worker tests. |
| T18 High | **Accidental mainnet execution**: Signer or RPC configuration points to mainnet. Preconditions: Misconfiguration/copy-paste. | Real assets at risk. | Configured chain/genesis and exact isolated account/token assertions, Testnet-only mode; no arbitrary network field. | Root administrator can change config/build. | Wrong genesis/RPC/account/token fail closed before signing. |
| T19 Medium | **Missing or changed recipient storage**: Registration disappears after check. Preconditions: Recipient unregisters or unsupported storage implementation. | Failed attempt and fees. | Separate approved registration, storage callback then trusted atomic token failure handling. | TOCTOU cannot be eliminated by preflight alone. | Missing storage, malformed view and unregister interleaving integration tests. |
| T20 Medium | **Pause / expiry denial of safe completion**: Global pause blocks a success callback. Preconditions: Shared pause guard copied into callback. | Delivered funds indefinitely reserved. | Block new initiation and storage-stage dispatch, not settlement of existing attempt. | Recovery may still need humans after callback failure. | Pause/expiry/token delist immediately before final callback. |
| T21 Medium | **Dashboard presents reservation as payment**: List is stale or DB job says success with no canonical proof. Preconditions: Read API/display ambiguity. | False operational confidence. | Separate reservation, dispatch, delivery and settlement; show evidence/lag; chain status authoritative. | Read-only list depends on persisted job discovery. | Direct detail versus lagging list, missing evidence and conflicting DB status tests. |

## Security acceptance boundaries

The current contract lacks native execution. Existing manual verifier settlement is
intentional trusted attestation, not a discovered unrestricted public drain; it becomes
a critical bypass if new native payouts can enter that path. Operator-only reservation
does not authorize spending. Backend authorization hashes and DB leases are useful
supplementary controls, never substitutes for contract guards.

The existing FullAccess deployment key, mutable token implementation and recovery
attestor collusion cannot be eliminated by the proposed callback mechanism. Do not
claim trustless recovery, root-resistant custody or production readiness. Unknown
outcomes freeze funds. Liveness loss is preferable to duplicate transfer. No generic
rescue method or wallet advance is proposed.

Required review evidence: complete method-mode guard matrix, measured real promise
graph and failure tests, immutable binding fixtures, sidecar compatibility snapshots,
two-person recovery decisions and operational key/token governance review. Live
recipient, concrete approver/executor/verifier identities, TTL/gas constants and
upgrade signer availability remain unverified. These gate later work, not design documentation.
